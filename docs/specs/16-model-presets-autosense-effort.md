# Spec 16 — Model Presets, Window Autosense, and `/effort`

**Status:** Draft, revision 15 (fourteen design-critic, fourteen security-critic and seven friction-critic passes; the closing round's two signed resolutions of 2026-10-09 and its implementer notes folded in, see §12)
**Version target:** 0.18.0
**API version:** `PLUGIN_API_VERSION` unchanged ("1")

---

## 1. Problem

Three things went wrong in the same way on the reference box (RTX 5090, llama.cpp, Swift-1.5 27B NVFP4) across two days of sessions, and every one of them is a harness-level gap, not a user mistake:

1. **The served window was a quarter of what the model supports and nobody was told.** The server reported `n_ctx = 65536` on `/props` and `n_ctx_train = 262144` beside it on `/v1/models`. `init` and `doctor` read the first and never the second. The same model had served 131072 the day before, 105 requests, largest prompt 71.5K tokens, no memory error. The `-c 65536` came from a hand-written profile script the harness cannot see.
2. **Replies ended at the window with nothing visible.** Six `finish_reason=length` actions on Oct 7, each at 91–99% context fill, each with 16–37K characters of hidden reasoning and zero or truncated visible text. Two of them ended a critic's turn ("empty reply twice"). Nothing bounds the model's reasoning per request.
3. **Changing models is outside the harness.** `/model` can hot-swap, rebind to a peer, or cold-launch a peer (spec 13), but `init` only writes a launchable server for vLLM. A llama.cpp user ends up with systemd units and profile scripts, and `/model` cannot drive them.

A fourth, smaller one: every orchestrator↔critic switch re-prefilled ~50K tokens because the server's host prompt cache (default 8 GB) skipped states larger than that, on a box with 61 GB of RAM.

## 3. Goals

- G1. A **preset** is a named entry in the model tree spec 13 already defines: the primary `server:` block or an `extra_endpoints[]` peer with a `lifecycle`. It fully describes a launchable model: runtime, weights, context, cache types, flags, default effort. `init` writes them; `/model <name>` and `localharness model <name>` switch to them through the existing resolution branches. **No new config type.**
- G2. **Autosense the window.** At `init`, `start` and `doctor`, the harness knows the served window, the model's trained window, and the window that fits free memory, and says so in one line when they disagree — `start` the first time, and again only when the numbers change.
- G3. **Size `-c` when the harness launches.** A record without an explicit context gets the computed fit, capped at the trained window. Every margin is a config ratio with a documented default; no constant in code.
- G4. **Reasoning is bounded per request**, so a reply cannot spend the window on hidden thinking. A reply still cut at the window re-sends once with thinking off.
- G5. **`/effort off | low | high | max`**, arrow-key picker, per agent, inherited by children.
- G6. Existing hand-run servers keep working exactly as today. Everything here is additive.

## 4. Non-goals

- No new runtime support; the four in spec 13 stay the set.
- No multi-GPU placement. One accelerator, as today's GPU lock assumes.
- No change to the trust model's shape: launch keys stay machine-level and join the machine fingerprint (§9).
- `/reasoning` keeps its current meaning (display on/off). This spec adds `/effort`; it does not fold one into the other.
- No change to the loop's no-cap decision for `max_tokens` (see §7.5).

## 5. Config shape

A preset is `ManagedServerConfig`, which gains runtime-gated fields. Convention, stricter than today's docstring-only "vLLM only": the record's own validator, `_launch_target_present`, refuses the llama.cpp fields on `runtime: vllm` (not the cross-object `_lifecycle_requires_gpu`), and `bind_all`/`require_api_key` stop being vLLM-only because the llama.cpp branch gains both (§8). `binary` becomes **optional** on `runtime: llamacpp` (today `_launch_target_present` raises `runtime=llamacpp requires binary`, `config/models.py:1838–1841`): a record without one is *declared, not launchable*, and **every launch passes through one decision**, `launch_decision(spec, keyed) -> LaunchDecision` beside `required_key_kwargs` in `provider/server.py` (whose docstring already calls itself the one place that decision is made) — a frozen record of four fields, `(refusal: str | None, loopback: bool, key_file_ok: bool, note: str | None)`, never a narrowed copy of the spec, because `_active_heavy` holds the spec and `free_accelerator` compares by identity. `activate` is the one enforcement point — `SpawnedProcessStrategy.activate` for llama.cpp and `ManagedVllmStrategy.activate` for the vLLM binary and docker (`lifecycle.py:114–124`), since the narrowing applies to every runtime that honours the posture keys: it raises `.refusal` as `RuntimeError`, the shape of the Ollama and LM Studio refusals (`lifecycle.py:242–247, 380–384`) that every caller already prints as one line, and passes `loopback=`, `key_file_ok=` and the fit and `--cache-ram` it computes (both I/O) to `serve_command(spec, keyed=, loopback=, key_file_ok=, context=, cache_ram=)`, which stays free of I/O: llama.cpp and the vLLM binary append `--host 127.0.0.1` **last** whenever the launch binds loopback — the effective `bind_all` false or `loopback` set — so `bind_all` is the only exposure switch (llama-server keeps the last `--host` it sees, so a `--host 0.0.0.0` in `extra_args` cannot outlive the narrowing; ## 6. Window autosense

### 6.1 Three numbers, one line

`probe_served_window` grows a sibling `probe_window(base_url, model, provider_type, api_key=None) -> WindowProbe(served, trained)`; `probe_served_window` becomes `probe_window(...).served` so every current caller is unchanged. The llama.cpp branch sends `auth_headers` on both of its routes (`/props`, `/v1/models`), because neither is public on a keyed server and a keyed relaunch (§8) would otherwise silence the probe; callers pass `_launch_key(harness, base_url)`, which already resolves the primary's or the peer's key. The live 401 test in §11 also asserts the harness's own probe succeeds with the key. `start` calls `probe_window` once (`cli/start_cmd.py:1040`) and feeds both the window guard and the report from that one result; no second probe per start. `trained` comes from `meta.n_ctx_train` (llama.cpp, same `/v1/models` call), `max_model_len` (vLLM: served and trained coincide), the GGUF header via `resolve_gguf_path` (Ollama, LM Studio), else `None`. The two older probes in `init_cmd.py:89` and `doctor_cmd.py:555` are replaced by this call.

`init`, `start` and `doctor` print, when served and fit disagree by more than `notify_ratio` — `start` only when `served` or `trained` differs from the triple last recorded for this `(runtime, served_name)`, or `fits` moved by more than `notify_ratio` of the recorded value — `fits` is a live free-memory reading floor-divided by the per-token KV size, and a few-MiB wobble (a compositor, a browser, another session) moves it by whole tokens, so an exact compare would print on every start on a desktop box and `init`'s recorded triple would never equal `start`'s — a field on the speed ledger's own entry (`record_window_report`/`last_window_report` beside `record_tokens_per_chunk`, `provider/speed_stats.py:102–162`: the ledger already is a per-`speed_key` record that grows additive fields in place, and §8's ranking reads it; no second file) — so a unit that serves 65,536 every day is told once and again only when something changes; `init` records the triple it printed, so the first `start` after an import prints nothing new, and `start` records the triple whether or not it printed, so a unit that returns after a reboot with the same numbers stays silent; `doctor` always. The #127 line (`Context budget fitted to …`, `start_cmd.py:1050–1066`), which today prints on every start while the factory default exceeds the served window, keys on the same record and prints on change only; an import writes no context budget (an explicit pin would silently cap the loop after the harness's own larger relaunch — §1.1 reborn):

```
window: served 65,536 · trained 262,144 · fits 114,688 (free 6.0 GiB of 32.6 beside the served model; weights 18.5 GiB)
  → unset `server.context` to relaunch with -c 114688
```

The first line prints the free figure the fit used, so its numbers add up (§6.2). A fit that is not computed, or comes out at or below zero, is never turned into a `-c`: the launch omits `-c` and llama-server's own `--fit` sizes the window (`n_ctx` defaults to the trained window and `fit_params` is on in the user's build, `common/common.h:455, 481`), and the line says `window: served by llama-server's --fit` — never a refusal. A `-c` riding in a 0.17 record's `extra_args` wins, because `extra_args` follows every flag the harness generates (only the loopback `--host` comes after), so with such a `-c` present the launch carries no fit keyword and the §6.2 retry is skipped (halving the keyword would relaunch an identical argv), and the undo line names `server.extra_args` instead of `server.context`. The second line reads `unset server.context to relaunch with -c 114688` when the record sets a context (a hand edit may; an import never does, §8), `the next harness launch uses -c 114688` when it is unset and the server was launched by hand, and the one-line pointer to `init` when there is no `server:` record at all (nothing to unset, no harness launch). `doctor` gains one row, and its far-below branch stops hard-coding `reserve = 4_096` and `0.75`: the reserve is `response_reserve(served)`, as the exceeds branch already does since 26acff1 (a reserve knob under `autosense:` would be a second owner beside the one place the harness reserves it), and the "wasting more than a quarter" test is `1 − notify_ratio`, the same 25% idea on the config-vs-served pair. No constant moves and `autosense:` gains no reserve key.

### 6.2 The fit

```
fits = floor( (free_bytes − weights_bytes − compute_margin) / kv_bytes_per_token ), capped at trained
compute_margin     = compute_margin_ratio × weights_bytes
kv_bytes_per_token = n_layer × 2 × n_head_kv × head_dim × bytes(cache_type)
```

- `free_bytes`: `nvidia-smi --query-gpu=memory.free,memory.total --format=csv,noheader,nounits` through `which_outside_cwd`, each line parsed with `int()` in a `try`; `[N/A]` (unified memory, `lifecycle.py:536–540`) falls to `MemAvailable − unified_reserve_ratio × MemTotal`. The fit is one function, `fit(header, free_bytes, ratios, attached_served: int | None)`, with `attached_served` set when the record's served name answered at its `base_url`: the incumbent is then this record's own server, which the relaunch replaces, and it holds weights + margin + `served × kv_bytes_per_token`, so `fits = min(trained, served + floor(free_bytes / kv_bytes_per_token))` — no pid and no per-process query (`nvidia-smi --query-gpu` cannot attribute bytes to a process, and the liveness oracle reports no pidfile for an imported unit, the very case of the §6.1 example), and it errs low when the real footprint is larger; without an attached incumbent the formula above applies, and under a serving unit it would otherwise give `fits ≤ 0` on every start. The tolerance is `notify_ratio` itself, one meaning — a difference worth telling — across the line's gate, its hysteresis and `doctor`'s `1 − notify_ratio`; not a second knob. `weights_bytes` counts only the GPU-resident bytes (§6.3's host-resident rule); when the offload cannot be sized (`-ot`, `--n-cpu-moe`, the box's own Flash-Next profile) the fit is "not computed" and the launch carries no `-c` (§6.1). At `init`, `attached_served` is set from the user-owned pid on the port running the record's `-m` with its `-c` (a `-c 0` counts as `trained`), since a keyed unit answers 401 to an `init` that holds no key; a wrong value only feeds the fit and costs one halve-once retry. Other processes on the card are part of "used"; the harness never evicts them.
- `weights_bytes`: the GPU-resident bytes (§6.3's host-resident rule) of the GGUF, summed over a split's shards, plus mmproj; directory size for a checkpoint.
- `n_layer, n_head_kv, head_dim`: the fit calls `read_header(path, want={block_count, head_count_kv, key_length, context_length})` in `agent/gguf_header.py` (new, ≤120 lines, next to `agent/gguf_tokenizer.py`): the file is opened through `open_regular` (`core/private_files.py`: `O_RDONLY | O_NONBLOCK | O_NOCTTY | O_CLOEXEC`, then `fstat`-checked `S_ISREG` — a plain `open()` on a FIFO would block before any check could run, a regular file ignores `O_NONBLOCK` — so a FIFO or a symlink to a device is refused without hanging); magic and version check; `kv_count ≤ 4096`; string length ≤ 1 MiB; string arrays are walked under a named count cap (`tokenizer.ggml.tokens` is ~150K strings) within a total header-byte budget that admits a ~11 MB KV section, so a caller's `want` can lie past `tokenizer.ggml.merges` (§8's `split.no`); it stops once every wanted key is read — here `<arch>.block_count`, `<arch>.attention.head_count_kv`, `<arch>.attention.key_length` (fallback `embedding_length / head_count`) and `<arch>.context_length` — and never touches tensor infos. **No new dependency.** The same reader supplies `trained` for Ollama/LM Studio GGUFs. Impact of a hostile file is a refused read, never execution.
- For `runtime: vllm` the fit is not computed; `--max-model-len` is the user's and vLLM reports it.
- Verification after launch: compare `/props` (with the key) with what was asked. A served window **smaller** than asked is a mismatch, not a failure: the window line prints both numbers, and `_effective_max_context` (`cli/start_cmd.py:338`) already bounds the loop to `min(config, served)`. A probe that returns `None` is reported as "not verified" and is never treated as a failed start — the loop then runs on the config value, where §7.4.1's overflow handling surfaces any consequence; only a dead process (pidfile pid + start time gone) or a load failure in the log's last lines counts. On that, verified-stop the failed process (`stop_server`), halve the `-c` keyword once (no `-c`, no retry), relaunch, then give up with the server's last log lines. One retry, bounded, no search.

### 6.3 Prompt cache

For `runtime: llamacpp`, `cache_ram` unset passes `--cache-ram` = `cache_ram_ratio × (MemAvailable − host-resident weight bytes)`, clamped at `cache_ram_ceiling_ratio × MemTotal`. Host-resident weight bytes are the GGUF size when `-ngl` is below the layer count or `--no-mmap` is present, else 0. `0` passes `--cache-ram 0`.

## 7. `/effort`

### 7.1 Surface

- `/effort` (the dispatcher row `_slash_effort`, handled by `_handle_effort_cmd` beside `_handle_model_cmd`, both new) with no argument opens an arrow-key picker: `off  low  high  max`, current level highlighted, Enter selects, Esc leaves it. `/effort <level>` sets it directly. `/effort show` prints the resolved level of the session agent and of every agent file that sets its own.
- The picker is a new small widget (`cli/picker.py`, prompt_toolkit) with the same keys as the input box; `/model` and the preset chooser reuse it in a later change.
- Terminal and mobile get the picker; Discord gets `/effort <level>` only. `/effort` is a core `SlashCommand` row, not `terminal_only`.

### 7.2 Where the level lives

Named `effort` everywhere, never `reasoning`, to keep the owner's separation from `/reasoning` and `terminal.show_reasoning`. The ratio section is `effort_budget:` so no key named `effort` ever holds anything but a level.

Precedence, highest first:

```
/effort (session)  >  agent file `effort`  >  division `effort`  >  the serving endpoint's persisted effort  >  org.default_effort  >  schema default (high)
```

Resolution is split the way the model chain already is: the loader resolves agent > division through `_resolve_scalar(..., org_val=None, default="inherit")` (it never sees the harness section), and one pure resolver — `resolve_effort(session, agent_file, harness, base_url) -> (level, rung)` in a new `config/effort.py`, the only place the ladder is spelled — is called by `start`, `/effort`, `/model` and `/effort show` where the active endpoint is known, as `start_cmd` resolves the model chain. The result is **set on the loop, never written into `AgentConfig.effort`**, which stays the agent file's own rung (below).

- `agents/<name>.yaml` → `effort: off|low|high|max|inherit` (new `AgentConfig` field, default `inherit`); `DivisionConfig` gets the same optional field.
- `org.default_effort: Optional[...]` is the machine default, spelled like `default_model`/`default_temperature`; as an `Optional` with default `None` it needs no `model_fields_set` guard.
- A record's `effort` (`server.effort`, `extra_endpoints[<name>].lifecycle.effort`) is the preset's **default**, written by `init` or by hand.
- **The serving endpoint's persisted effort** is resolved from the live `base_url`, never from whatever record happens to be on disk: `server.effort` when `base_url == provider.base_url`; `active_endpoint.effort` only when `active_endpoint.base_url == base_url`, falling back to that peer's `lifecycle.effort`; otherwise the rung is skipped. `start` runs on the primary and never reads `active_endpoint` back (its own note says so), and `/model <primary>` goes through `persist_default_model`, which leaves `active_endpoint` untouched — so a peer's `max` recorded there can reach the primary neither after a switch back nor at a restart, the stale-state class `persist_active_endpoint` exists to prevent.
- `/effort` applies to the session at once and **persists only to dict paths** (through `persist_effort` in `cli/model_ops.py`, new, beside `persist_default_model`): `server.effort` when the primary serves, a new `active_endpoint.effort` field on `ActiveSelection` when a peer serves, and `org.default_effort` when the primary is a hand-run server with no `server:` block (the only rung below it that exists). It never writes `extra_endpoints` through the overlay: `deep_merge` would replace the whole peer list and `set_value_in_dict` cannot address a list element, so an overlay write would copy every peer's `api_key` and `extra_headers` into `overrides.yaml` and shadow `config.yaml`'s list. `persist_active_endpoint` clears `effort` on a switch the way it clears `api_key`: there is no unset primitive in `registry/paths.py` or `config/overlay.py`, so it is the existing comprehension filter over the previous `active_endpoint` dict (`model_ops.py:245–250`) widened from `{api_key}` to `{api_key, effort}` before the keys are re-set. `effort` is **never a fingerprinted key** (§9).
- The write goes through `model_ops`'s validate-then-`atomic_write_overlay` path with a `ComponentMutated` audit row whose `actor` is the new literal `"channel"` with the channel identity in `actor_detail` (`core/events.py:527` widened, `actor_detail` already exists), so a Discord `/effort` is audited rather than failing validation after the write.
- A child with `inherit` takes the parent's effective level **per request, never at construction**. `max_context_tokens` is a construction-time argument of the runner (`cli/start_cmd.py:1518`, `agent/subagent.py:1337`) and of the `ContextManager`; threading effort that way would freeze the start-time level, and a mid-session `/effort` would never reach a child. **The effective level lives on the loop, not on `AgentConfig`:** `AgentLoop` gains `self._effort: Level | None = None` and `self._effort_rung: str | None`, one mutator `set_effort(level, rung)` — a `set_<x>()` method like `gate.set_mode` and `context.set_iteration`, the tree's thirteen-to-one convention over property setters, and the spelling spec 17 uses for `set_session_id` — and two read-only properties, `effective_effort` and `effort_rung`. `None` means **no effort keys are sent**, today's request byte for byte, which is what the eight `AgentLoop(` constructors outside `start` get (`bench/runner.py:376, 615`; `subagent.py:566, 645, 723, 900, 1075, 1108` — nine in all with `start_cmd.py:1562`): a bench or cruncher loop nobody configured runs exactly as today, with no magic default. `AgentConfig.effort` is never overwritten — it is the file's rung, and overwriting it with the collapsed level would make a later `/model <peer>` re-resolve from a clobbered rung: `agent_config.effort == high`, written by `start` from `server.effort`, would read as an agent-file level outranking the peer's `lifecycle.effort: max`, and `/effort show` could no longer name the rung. The `max_context_tokens` precedent (`start_cmd.py:1066`, `repl.py:2087–2121`) does not have this problem because the refit re-reads an untouched source and overwrites only the scalar. `start` calls `resolve_effort(None, agent_config.effort, harness, base_url)` and builds the loop with `AgentLoop(..., effort=(level, rung))` — a constructor keyword defaulting to `None`, so every existing constructor stays byte-identical — while `set_effort` serves the REPL's mid-session change; the REPL keeps the session rung in `self._session_effort` (set by `/effort`, `None` until then), re-resolves with it on `/effort` and after every `/model` switch — at `_refresh_token_counter` (`repl.py:2053`), where all four `/model` branches land (`:1589, 1615, 1696, 1787`) and where the window refit already rewrites the loop's `_ctx` in place, the one post-switch point — and calls `set_effort` on the loop it holds as `self._agent`, the way `/mode` reaches the shared gate through `gate.set_mode`. `make_explore_agent_runner` gains a zero-argument `effort_fn` returning the loop's own `(effective_effort, effort_rung)` — zero-argument because the runner is built before the loop exists (`start_cmd.py:1512` vs `:1562`), the `get_parent_session_id` shape (`subagent.py:1333`) — read at each dispatch and re-threaded into the nested runner that `_build_child_agent_tool` rebuilds for a non-leaf child (`subagent.py:1410–1431`, where `max_context_tokens` is re-threaded), so a grandchild reads the live level too. The dispatch seam never holds a loop — each `dispatch_*` builds its own `AgentLoop` and calls `run_turn` at once (`:566→578`, `:645`, `:723`, `:900`, `:1075`, `:1108`) — so the child's level rides every dispatcher as a keyword the way `config_dir`/`state_dir` do (`:1497–1527`) and lands in the child's constructor `effort=`: the parent's level when the parent's rung is `session` (the person's `/effort` outranks every file), else the child's own file level when it is not `inherit`, else the parent's level — the §7.2 order without a `HarnessConfig` at dispatch. ### 7.3 What a level means

| Level | Thinking | Reasoning budget for the request |
|---|---|---|
| off | disabled | 0 |
| low | on | `effort_budget.low_ratio` × output headroom |
| high | on | `effort_budget.high_ratio` × output headroom |
| max | on | unbounded |

Headroom is `_window_headroom` with its `1/64` margin moved to `autosense.template_margin_ratio`. The level enum is the only thing an agent file can set; the number is always derived.

### 7.4 Enforcement, in order of preference

1. **Per-request budget.** llama.cpp: `extra_body={"reasoning_budget_tokens": N}` through `_native_kwargs`.
