# Spec 16 — Model Presets, Window Autosense, and `/effort`

**Status:** Draft, revision 7 (six design-critic and six security-critic passes; iteration-6 findings folded in; design verdict SHIP at iterations 5 and 6)
**Version target:** 0.18.0
**API version:** `PLUGIN_API_VERSION` unchanged ("1")

---

## 1. Problem

Three things went wrong in the same way on the reference box (RTX 5090, llama.cpp, Swift-1.5 27B NVFP4) across two days of sessions, and every one of them is a harness-level gap, not a user mistake:

1. **The served window was a quarter of what the model supports and nobody was told.** The server reported `n_ctx = 65536` on `/props` and `n_ctx_train = 262144` beside it on `/v1/models`. `init` and `doctor` read the first and never the second. The same model had served 131072 the day before, 105 requests, largest prompt 71.5K tokens, no memory error. The `-c 65536` came from a hand-written profile script the harness cannot see.
2. **Replies ended at the window with nothing visible.** Six `finish_reason=length` actions on Oct 7, each at 91–99% context fill, each with 16–37K characters of hidden reasoning and zero or truncated visible text. Two of them ended a critic's turn ("empty reply twice"). Nothing bounds the model's reasoning per request.
3. **Changing models is outside the harness.** `/model` can hot-swap, rebind to a peer, or cold-launch a peer (spec 13), but `init` only writes a launchable server for vLLM. A llama.cpp user ends up with systemd units and profile scripts, and `/model` cannot drive them.

A fourth, smaller one: every orchestrator↔critic switch re-prefilled ~50K tokens because the server's host prompt cache (default 8 GB) skipped states larger than that, on a box with 61 GB of RAM.

## 3. Goals

- G1. A **preset** is a named entry in the model tree spec 13 already defines: the primary `server:` block or an `extra_endpoints[]` peer with a `lifecycle`. It fully describes a launchable model: runtime, weights, context, cache types, flags, default effort. `init` writes them; `/model <name>` and `localharness model <name>` switch to them through the existing resolution branches. **No new config type.**
- G2. **Autosense the window.** At `init`, `start` and `doctor`, the harness knows the served window, the model's trained window, and the window that fits free memory, and says so in one line when they disagree.
- G3. **Size `-c` when the harness launches.** A record without an explicit context gets the computed fit, capped at the trained window. Every margin is a config ratio with a documented default; no constant in code.
- G4. **Reasoning is bounded per request**, so a reply cannot spend the window on hidden thinking. A reply still cut at the window re-sends once with thinking off.
- G5. **`/effort off | low | high | max`**, arrow-key picker, per agent, inherited by children.
- G6. Existing hand-run servers keep working exactly as today. Everything here is additive.

## 4. Non-goals

- No new runtime support; the four in spec 13 stay the set.
- No multi-GPU placement. One accelerator, as today's GPU lock assumes.
- No change to the trust model's shape: launch keys stay machine-level and join the machine fingerprint (§9).
- `/reasoning` keeps its current meaning (display on/off). This spec adds `/effort`; it does not fold one into the other.
- No change to the loop's no-cap decision for `max_tokens` (see §7.5).

## 5. Config shape

A preset is `ManagedServerConfig`, which gains runtime-gated fields. Convention, stricter than today's docstring-only "vLLM only": the record's own validator, `_launch_target_present`, refuses the llama.cpp fields on `runtime: vllm` (not the cross-object `_lifecycle_requires_gpu`), and `bind_all`/`require_api_key` stop being vLLM-only because the llama.cpp branch gains both (§8). Every derived field is spelled the way the tree spells "not set": `Optional[int] = None`, where `None` means "the harness computes it"; no `"auto"` literal enters the schema.

## 6. Window autosense

### 6.1 Three numbers, one line

`probe_served_window` grows a sibling `probe_window(base_url, model, provider_type, api_key=None) -> WindowProbe(served, trained)`; `probe_served_window` becomes `probe_window(...).served` so every current caller is unchanged. The llama.cpp branch sends `auth_headers` on both of its routes (`/props`, `/v1/models`), because neither is public on a keyed server and a keyed relaunch (§8) would otherwise silence the probe; callers pass `_launch_key(harness, base_url)`, which already resolves the primary's or the peer's key. The live 401 test in §11 also asserts the harness's own probe succeeds with the key. `start` calls `probe_window` once (`cli/start_cmd.py:1040`) and feeds both the window guard and the report from that one result; no second probe per start. `trained` comes from `meta.n_ctx_train` (llama.cpp, same `/v1/models` call), `max_model_len` (vLLM: served and trained coincide), the GGUF header via `resolve_gguf_path` (Ollama, LM Studio), else `None`. The two older probes in `init_cmd.py:89` and `doctor_cmd.py:551` are replaced by this call.

`init`, `start` and `doctor` print, when served and fit disagree by more than `notify_ratio`:

```
window: served 65,536 · trained 262,144 · fits 139,264 (free 6.0 GiB of 32.6; weights 18.5 GiB)
  → unset `server.context` to relaunch with -c 131072
```

The second line reads `unset server.context to relaunch with -c 131072` when the record sets a context (an import may, §8), `the next harness launch uses -c 131072` when it is unset and the server was launched by hand, and the import offer of §8 when there is no `server:` record at all (nothing to unset, no harness launch). `doctor` gains one row and its `reserve = 4_096` / `0.75` constants move to the same `autosense:` section while it is being touched.

### 6.2 The fit

```
fits = floor( (free_bytes − weights_bytes − compute_margin) / kv_bytes_per_token ), capped at trained
compute_margin     = compute_margin_ratio × weights_bytes
kv_bytes_per_token = n_layer × 2 × n_head_kv × head_dim × bytes(cache_type)
```

- `free_bytes`: `nvidia-smi --query-gpu=memory.free,memory.total --format=csv,noheader,nounits` through `which_outside_cwd`, each line parsed with `int()` in a `try`; `[N/A]` (unified memory, `lifecycle.py:536–540`) falls to `MemAvailable − unified_reserve_ratio × MemTotal`. Other processes on the card are part of "used"; the harness never evicts them.
- `weights_bytes`: file size for a GGUF plus mmproj; directory size for a checkpoint.
- `n_layer, n_head_kv, head_dim`: a ≤120-line header reader next to `agent/gguf_tokenizer.py`: the file is opened with `os.open(path, O_RDONLY | O_NONBLOCK | O_NOCTTY | O_CLOEXEC)` and then `fstat`-checked `S_ISREG` (a plain `open()` on a FIFO would block before any check could run; a regular file ignores `O_NONBLOCK`), so a FIFO or a symlink to a device is refused without hanging; magic and version check; `kv_count ≤ 4096`; string length ≤ 1 MiB; array values are skipped by `seek` over `count × element size` with `count` bounded by a named constant (`tokenizer.ggml.tokens` is ~150K strings and is never read); a total header-byte budget; stops once `<arch>.block_count`, `<arch>.attention.head_count_kv`, `<arch>.attention.key_length` (fallback `embedding_length / head_count`) and `<arch>.context_length` are read; never touches tensor infos. **No new dependency.** The same reader supplies `trained` for Ollama/LM Studio GGUFs. Impact of a hostile file is a refused read, never execution.
- For `runtime: vllm` the fit is not computed; `--max-model-len` is the user's and vLLM reports it.
- Verification after launch: compare `/props` (with the key) with what was asked. A served window **smaller** than asked is a mismatch, not a failure: the window line prints both numbers, and `_effective_max_context` (`cli/start_cmd.py:338`) already bounds the loop to `min(config, served)`. A probe that returns `None` is reported as "not verified" and is never treated as a failed start — the loop then runs on the config value, where §7.4.1's overflow handling surfaces any consequence; only a dead process (pidfile pid + start time gone) or a load failure in the log's last lines counts. On that, verified-stop the failed process (`stop_server`), halve `context` once, relaunch, then give up with the server's last log lines. One retry, bounded, no search.

### 6.3 Prompt cache

For `runtime: llamacpp`, `cache_ram` unset passes `--cache-ram` = `cache_ram_ratio × (MemAvailable − host-resident weight bytes)`, clamped at `cache_ram_ceiling_ratio × MemTotal`. Host-resident weight bytes are the GGUF size when `-ngl` is below the layer count or `--no-mmap` is present, else 0. `0` passes `--cache-ram 0`.

## 7. `/effort`

### 7.1 Surface

- `/effort` with no argument opens an arrow-key picker: `off  low  high  max`, current level highlighted, Enter selects, Esc leaves it. `/effort <level>` sets it directly. `/effort show` prints the resolved level of the session agent and of every agent file that sets its own.
- The picker is a new small widget (`cli/picker.py`, prompt_toolkit) with the same keys as the input box; `/model` and the preset chooser reuse it in a later change.
- Terminal and mobile get the picker; Discord gets `/effort <level>` only. `/effort` is a core `SlashCommand` row, not `terminal_only`.

### 7.2 Where the level lives

Named `effort` everywhere, never `reasoning`, to keep the owner's separation from `/reasoning` and `terminal.show_reasoning`. The ratio section is `effort_budget:` so no key named `effort` ever holds anything but a level.

Precedence, highest first:

```
/effort (session)  >  agent file `effort`  >  division `effort`  >  the serving endpoint's persisted effort  >  org.default_effort  >  schema default (high)
```

Resolution is split the way the model chain already is: the loader resolves agent > division through `_resolve_scalar(..., org_val=None, default="inherit")` (it never sees the harness section), and `start`/dispatch resolve the remaining rungs at runtime where the active endpoint is known, as `start_cmd` resolves the model chain.

- `agents/<name>.yaml` → `effort: off|low|high|max|inherit` (new `AgentConfig` field, default `inherit`); `DivisionConfig` gets the same optional field.
- `org.default_effort: Optional[...]` is the machine default, spelled like `default_model`/`default_temperature`; as an `Optional` with default `None` it needs no `model_fields_set` guard.
- A record's `effort` (`server.effort`, `extra_endpoints[<name>].lifecycle.effort`) is the preset's **default**, written by `init` or by hand.
- **The serving endpoint's persisted effort** is resolved from the live `base_url`, never from whatever record happens to be on disk: `server.effort` when `base_url == provider.base_url`; `active_endpoint.effort` only when `active_endpoint.base_url == base_url`, falling back to that peer's `lifecycle.effort`; otherwise the rung is skipped. `start` runs on the primary and never reads `active_endpoint` back (its own note says so), and `/model <primary>` goes through `persist_default_model`, which leaves `active_endpoint` untouched — so a peer's `max` recorded there can reach the primary neither after a switch back nor at a restart, the stale-state class `persist_active_endpoint` exists to prevent.
- `/effort` applies to the session at once and **persists only to dict paths**: `server.effort` when the primary serves, a new `active_endpoint.effort` field on `ActiveSelection` when a peer serves, and `org.default_effort` when the primary is a hand-run server with no `server:` block (the only rung below it that exists). It never writes `extra_endpoints` through the overlay: `deep_merge` would replace the whole peer list and `set_value_in_dict` cannot address a list element, so an overlay write would copy every peer's `api_key` and `extra_headers` into `overrides.yaml` and shadow `config.yaml`'s list. `persist_active_endpoint` clears `effort` on a switch the way it clears `api_key`: there is no unset primitive in `registry/paths.py` or `config/overlay.py`, so it is the existing comprehension filter over the previous `active_endpoint` dict (`model_ops.py:245–250`) widened from `{api_key}` to `{api_key, effort}` before the keys are re-set. `effort` is **never a fingerprinted key** (§9).
- The write goes through `model_ops`'s validate-then-`atomic_write_overlay` path with a `ComponentMutated` audit row whose `actor` is the new literal `"channel"` with the channel identity in `actor_detail` (`core/events.py:527` widened, `actor_detail` already exists), so a Discord `/effort` is audited rather than failing validation after the write.
- A child with `inherit` takes the parent's effective level **per request, never at construction**. `max_context_tokens` is a construction-time argument of the runner (`cli/start_cmd.py:1518`, `agent/subagent.py:1337`) and of the `ContextManager`; threading effort that way would freeze the start-time level, and a mid-session `/effort` would never reach a child. Instead the level lives on the shared `AgentConfig` instance the loop already reads per request (`self._config`, e.g. `loop.py:2436`): `/effort` mutates `agent_config.effort` in place and persists, the next request sees it, and the loop exposes a read-only `effective_effort` (the ladder resolved with the endpoint rung). `make_explore_agent_runner` gains a zero-argument `effort_fn` (`lambda: loop.effective_effort`) read at each dispatch, so a child built after `/effort` inherits the new level. Agent turns pass no `disable_thinking` today (`loop.py:1584–1588`); the level is what §7.4 turns into the request keys.
- `/effort show` prints the resolved level for the session agent and the rung it came from, plus every agent file that sets its own.

### 7.3 What a level means

| Level | Thinking | Reasoning budget for the request |
|---|---|---|
| off | disabled | 0 |
| low | on | `effort_budget.low_ratio` × output headroom |
| high | on | `effort_budget.high_ratio` × output headroom |
| max | on | unbounded |

Headroom is `_window_headroom` with its `1/64` margin moved to `autosense.template_margin_ratio`. The level enum is the only thing an agent file can set; the number is always derived.

### 7.4 Enforcement, in order of preference

1. **Per-request budget.** llama.cpp: `extra_body={"reasoning_budget_tokens": N}` through `_native_kwargs`. The sticky 400 handling becomes **per key**: one `_extra_body(disable_thinking, budget)` assembler serves all three request paths (today the two XML paths build it unguarded), `_remember_native_rejection` keeps a set of rejected keys with a classifier substring per key (`chat_template_kwargs`/`enable_thinking` for thinking-off; `reasoning_budget_tokens` for the budget; the bare `"extra_body"` substring no longer counts), a 400 that names neither key is retried **once** without any effort key, the way the native path already retries a dropped `tools` param; the keys are recorded as rejected **only when that retry succeeds** — when it fails too, the set is restored and the **original** error surfaces, so the tree's rule stands ("a genuinely malformed 400 must still surface, never a blanket retry"). A context-overflow 400 (`exceed_context_size_error`, what llama.cpp answers for a prompt that no longer fits — the very regime §1 describes) therefore leaves the set untouched (tested), and because its body names that type it is surfaced at once without the retry, saving one full prefill at 91–99% fill; without this rule one ordinary overflow would switch the budget off for the rest of the session. The set resets where the sticky booleans reset today (`rebind_endpoint`). A build that rejects one key does not silently drop the other. A rejected key is reported once in the start summary and by `/effort show` ("effort unenforced on this server: `reasoning_budget_tokens` rejected"); a key rejected after the summary has printed is announced once on the channel with the same line, never only in the log — the client has no channel, so the REPL diffs `llm.rejected_effort_keys` after each turn and prints the line for a newly rejected key. The client keeps a small per-runtime capability table beside its existing shape tables: `llamacpp → reasoning_budget_tokens`; `vllm → none` until a budget field is verified on the user's vLLM build (§12). The client counts reasoning **characters** in the stream (`client.py:1441–1445`), so the budget it hands the server is tokens and the budget it watches itself is an estimate; quality only.
2. **Request flag for `off`.** `chat_template_kwargs.enable_thinking=false`, the existing `disable_thinking` path, now reachable for agent turns. The `complete()`/`_native_kwargs` docstrings that forbid `disable_thinking` on agent turns (#11) are superseded for this one use and say so.
3. **Loop-owned cut, only where 1 is unavailable.** The established mid-stream abort pattern is reused, not a new mechanism: the client's `_abort` hook raises `ProviderReasoningBudgetError(budget, spent)` when the stream's reasoning passes the budget; the loop catches it beside `ProviderDegenerateError`, publishes `Action(finish_reason="reasoning_cut", reasoning_chars=spent)` (the field exists), and re-sends the **identical message list** once with `disable_thinking=True` under a new `session.reasoning_cut_used` flag. Never a partial assistant prefix; a second cut in the same turn ends the turn the way a second degenerate abort does. No `ReasoningCut` event type; the client has no bus and knows no `agent_id`. When thinking-off is itself a rejected key on that server, the cut is skipped and the start summary says so.

### 7.5 `max_tokens` stays as it is

The loop's decision (`loop.py:2419–2426`) stands: unconfigured means no `max_tokens` is sent. Problem 2 is fixed by the reasoning budget, not by a cap. The one addition sits inside today's empty-completion branch (`loop.py:1868–1891`) and keeps the one-retry-per-shape convention: when `finish_reason == "length"` and no cap was sent, the single retry is the identical re-send with thinking off, spending `empty_reprompt_used`, instead of the `_EMPTY_REPLY_NUDGE` (which would push more tokens into a 91–99%-full window); every other empty reply keeps the nudge. `_EMPTY_TURN_NOTICE` stops saying "raise the model's max output tokens" for the no-cap case and names the window instead.

## 8. `init` and switching

- `init` discovers: GGUF files under `autosense.model_roots` (default `~/models` and the paths `resolve_gguf_path` already knows), with a bounded walk — `lstat`-filtered to regular `.gguf` files, symlinked directories never descended, named depth and file-count caps — since the agent can write under those roots; running servers (as today); and `llama-server`/`vllm`/`ollama`/`lms` through `which_outside_cwd` (never a bare name for `Popen`). It writes the first discovered GGUF as `server:` with `context` unset (the fit) and the rest as `extra_endpoints[]` peers with `lifecycle`, naming each from its filename, and asks which should serve. Nothing is launched by `init` unless the user says so; today's vLLM guided setup becomes "write the record, then offer to launch".
- **What `provider:` is written when nothing is launched.** `_write_config` today derives `default_model`, `available_models`, the capability probe and the window from a live server. With a record and no server: `base_url = http://127.0.0.1:<port>/v1`, `default_model = served_name`, `available_models = [served_name]`, `supports_function_calling` left to the first `start`'s capability probe, the window to the existing auto-fit (#127). `ManagedServerConfig.model`'s docstring stops saying "passed to `vllm serve`".
- **Import** of a server the harness did not launch. `init` maps the port to a pid through `/proc/net/tcp*` inode → the user's own `/proc/<pid>/fd`. It then opens `/proc/<pid>` **once as a directory fd**, `fstat`s it for `st_uid == os.getuid()`, reads `cmdline`, `exe`, `cwd` and `stat` through `dir_fd=`, and reads the start time before and after so a pid reused mid-read is detected. `binary:` is `exe` only when its basename equals `argv[0]`'s basename (a console-script server such as `vllm` resolves `exe` to the interpreter); otherwise a **bare** `argv[0]` is resolved through `which_outside_cwd`, never against `cwd` — every agent subprocess shares the user's uid, so the ownership check proves nothing about intent, and a `./llama-server` in the process cwd is exactly the lookup that helper exists to refuse — while an `argv[0]` with a directory part is joined to the process's `cwd` explicitly before any lookup (`which_outside_cwd` hands a name with a directory part to plain `shutil.which`, which would look in the harness's own cwd, `core/which.py:18–19`). Relative model, mmproj and key-file paths are resolved against the process `cwd` the same way; absolute paths are written. Before anything is written, `init` shows the absolute `binary`, `model`, `mmproj` and the key-file **path** (never its content).
- **Secrets and binding on import.** The import reads `cmdline` **and `environ`** through the same directory fd (a systemd `Environment=` never shows in `cmdline`). Before anything is shown or written, key-shaped material is stripped from both: `--api-key` (a CSV of keys; more than one is refused), `--api-key-file` and `LLAMA_ARG_API_KEY_FILE` (a path, resolved against the process `cwd`), `VLLM_API_KEY`, `LLAMA_API_KEY`. A key found **inline** (argv or environment) goes to the `SecretStr api_key` + `require_api_key` path, never into `extra_args`; the import is refused if anything key-shaped remains. **A key file is a path the process chose, and the import acts on it only after a person has seen it.** The file is not opened during masking: its path is shown beside the other paths, and only after the person confirms them (the existing "which should serve" step; no new question) is it opened — refused unless it is a regular file holding one non-empty line, which is what llama-server reads — read into `SecretStr`, and used for `init`'s capability and window probes (§6.1), which run with the key only after that confirmation. Under `--no-input` there is no person, so an import carrying `--api-key-file` or `LLAMA_ARG_API_KEY_FILE` is refused with one line ("run init on a terminal to import a keyed server") and the file is never opened: the agent's shell tool can run `init --no-input`, and a listener whose `cmdline` names `~/.cache/huggingface/token` would otherwise have the harness read that token, send it as a bearer to the port holder, and persist it as `provider.api_key` for every later request. An inline key needs no such care: it is the process's own, and sending it back to that process reveals nothing. **Every** `--host`/`--port` argument (and `=` forms, and `LLAMA_ARG_HOST`/`LLAMA_ARG_PORT` from the environment) is removed from `extra_args`, and the effective host list — argv's `--host` when present, else `LLAMA_ARG_HOST`, which is how llama-server resolves it — is classified entry by entry, **by literal parsing, never DNS**: an entry is loopback when `ipaddress.ip_address(entry).is_loopback` (`127.0.0.1`, `127.0.0.2`, `::1`, `::ffff:127.0.0.1`) or is the one literal name `localhost`; an all-loopback list becomes nothing; any non-loopback **address** makes `bind_all: true` with a shown line; any other **hostname** (`ip6-localhost`, `localhost.evil.com`, a LAN name) refuses the import with the entry shown, because the harness cannot reproduce a name binding and must not widen it to every interface; a `.sock` entry refuses likewise, because the harness cannot relaunch a UNIX socket and must not relaunch a TCP listener in its place; the port becomes `port:`; nothing is left where it would override the harness's own `--host`. **The llama.cpp launch gains the key and bind paths it lacks today:** `start_server` gains a `runtime` parameter (today it takes only `config_dir, cmd, api_key`) and sets **`LLAMA_API_KEY`** (the variable llama-server actually reads) for `llamacpp` and `VLLM_API_KEY` otherwise, in the child's copied environment only, the name coming from one `KEY_ENV` table (`vllm → VLLM_API_KEY`, `llamacpp → LLAMA_API_KEY`) that `serve_command`'s docker `-e` also reads, so the mapping lives in one place. **The child's environment is the record plus the key and nothing else the server reads:** `start_server` copies `os.environ` minus every `LLAMA_ARG_*` and `LLAMA_API_KEY` for `llamacpp`, minus `VLLM_API_KEY` for `vllm`, and adds `KEY_ENV[runtime]` only when keyed — today an unkeyed launch passes `env=None` and inherits a shell `VLLM_API_KEY`, relaunching keyed with a key the harness does not know, and llama-server applies all ~150 `LLAMA_ARG_*` before argv, so a `LLAMA_ARG_API_KEY_FILE` or `LLAMA_ARG_N_GPU_LAYERS=0` in the harness's own environment (dotfiles, a systemd user environment, or `python_exec`, which runs in-process and can set `os.environ`) would reshape a relaunch the record and the fingerprint never see — the silent drop the import refuses on the unit's side. The dropped **names** are logged once per launch, never values; `SpawnedProcessStrategy.activate` passes `server.key_kwargs(api_key)` exactly as the container path does — the caller already gated through `_launch_key` → `required_key_kwargs`, so gating again inside `activate` would double-gate; and the llama.cpp branch of `serve_command` gets the same `bind_all → --host` switch vLLM has (the `bind_all` migration is vLLM-only, so no upgrade regression). A keyed import on a runtime that cannot carry a key is refused rather than relaunched open. `--verbose` in `extra_args` is shown with a note that llama-server then logs the key's last four characters. Tests: an imported `--host 0.0.0.0 --api-key K` relaunches with `LLAMA_API_KEY` in the environment and `K` absent from argv and `serve.log`, **and a live request without the bearer to the relaunched server returns 401 while the harness's own `probe_window` succeeds with the key**; `--host 192.168.1.5` yields `bind_all: true`; `--host 127.0.0.1,::1` and `--host 127.0.0.2` yield nothing; `--host ip6-localhost` and `--host /run/llama.sock` refuse; an env-only `LLAMA_ARG_HOST=0.0.0.0` yields `bind_all: true`; an `Environment=LLAMA_API_KEY=K` unit imports keyed; a planted `--api-key-file` path under `--no-input` is never opened (a `sys.addaudithook` on `open` records no event for it) and the import is refused with the one line, while interactively the file is opened only after the confirmation; a decoy `LLAMA_ARG_N_GPU_LAYERS` and a shell `VLLM_API_KEY` are absent from the relaunched child's environment, the one `KEY_ENV` variable present only when keyed, and the dropped names logged without values.
- **What the import consumes from `environ`, exactly.** A named list and nothing else: the key variables above; `LLAMA_ARG_HOST`/`LLAMA_ARG_PORT`; and the variables that map onto record fields — `LLAMA_ARG_MODEL → model`, `LLAMA_ARG_ALIAS → served_name`, `LLAMA_ARG_CTX_SIZE → context`, `LLAMA_ARG_CACHE_TYPE_K`/`_V → cache_type_k/v`, `LLAMA_ARG_CACHE_RAM → cache_ram`, `LLAMA_ARG_MMPROJ → mmproj` — with argv winning over the environment, as llama-server resolves them. llama-server applies about 150 `LLAMA_ARG_*` names (and the `LLAMA_ARG_NO_*` negations) before argv, and a harness relaunch inherits the harness's environment, never the unit's; so any **other** `LLAMA_ARG_*` present refuses the import with the variable **names** shown (never values) and the one-line fix "move them to the unit's argv" — never a silent drop that relaunches CPU-only, un-templated or on a different model. Two refuse outright, since no argv move helps, and both are checked on `cmdline` and `environ` alike through one table of (flag, env) pairs, **before** the record is validated, so the user reads the named line and never a pydantic error about a missing `model`: download identity — `-mu/--model-url` (`LLAMA_ARG_MODEL_URL`), `-dr/--docker-repo` (`LLAMA_ARG_DOCKER_REPO`), `-hf/-hfr/--hf-repo` (`LLAMA_ARG_HF_REPO`), `-hff/--hf-file` (`LLAMA_ARG_HF_FILE`), `-hfd/--hf-repo-draft` — with the line "a record needs a local path"; and TLS — `--ssl-key-file`/`--ssl-cert-file` (`LLAMA_ARG_SSL_KEY_FILE`, `LLAMA_ARG_SSL_CERT_FILE`) — because the harness cannot relaunch TLS and must not relaunch plaintext on the same interfaces. Nothing else in `environ` — `HF_TOKEN`, `OPENAI_API_KEY`, `AWS_*`, anything — is read into a value, shown, logged or written; a fixture with a decoy `HF_TOKEN` proves it.
- **An imported context is a choice, not a fact.** `-c` on argv or `LLAMA_ARG_CTX_SIZE` would otherwise freeze the unit's own `-c 65536` — the problem §1.1 exists for — into the record. `init` is already interactive (it asks which preset serves), so when the fit exceeds the imported context by more than `notify_ratio` it asks one line, `keep -c 65536 / let the harness fit (-c 131072)`, and writes `context: 65536` or leaves it unset accordingly. Under `--no-input` the imported value is written as-is and the window line says `unset server.context to relaunch with -c 131072`.
- **The import records nothing in the trust store.** `init --no-input` runs with no person, so the agent's shell tool can run it, and by §9's own rule `init` must never self-adopt. The next terminal start asks once about the new `server.binary`, `extra_args` and model keys, exactly as a hand edit does, or withholds `server:` where it cannot ask (tested).
- The user keeps or deletes their own unit afterwards; the harness never touches systemd.
- `/model <name>` resolves through today's four branches (serving here, peer running, cold, downloaded). A server the harness did not launch holding the port is refused with the pid and the port and the import offer. No signal is ever sent to a foreign process.
- **Pid reuse.** Because this spec adds launch/stop cycles (fit retry, preset switch), the pidfile records the process start time beside the pid, parsed after the last `)` of `/proc/<pid>/stat` the way `_is_zombie` already does. One `_same_process(pid, start)` helper is used by `server_pid`, `_alive`, `_wait_dead` and before every `killpg`, including the SIGKILL after the SIGTERM grace.
- The decode-speed ledger keys on `(runtime, served_name)` as today, so presets inherit their history.

## 9. Security

- **Machine-only.** `server` and `extra_endpoints` are already in `HARNESS_GLOBAL_ONLY_FIELDS`; `autosense` (including `model_roots`), `effort_budget` and `org.default_effort` are added. A workspace value is dropped with the existing one-line warning, as `server` is today. All ratios are bounded `(0, 1]` in pydantic.
- **Machine fingerprint.** Adoption is per **kind**, and `launch` is already in every record, so new entries go under kinds the record predates: **`launch_model`** = `server.{model, mmproj, served_name, context, cache_type_k, cache_type_v, cache_ram}`, and **`peer_launch`** = every `extra_endpoints[<name>].lifecycle.*` launch and model key (peer entries named by `name`, never by index, so re-ordering never re-prompts). `launch` keeps `server.{binary, docker_image, extra_args}` and gains **`bind_all` and `require_api_key`**, which decide the next launch's interfaces and key and are not fingerprinted today (`LAUNCH_KEYS`, `trust.py:189–190`): an agent-written `server.bind_all: true` in `overrides.yaml` widens the next launch to every interface with no ask, while the same widening through `extra_args: [--host, 0.0.0.0]` asks — pre-existing for vLLM, live on llama.cpp with this spec's `bind_all → --host`. Under `launch`, a recorded kind, they ask once at the next terminal start for the users who set them, the right side: a value planted before the upgrade must be seen, not adopted. `peer_launch` carries both for peers. The `peer_launch` entry shape is the `launch` kind's own: one entry per key, named `extra_endpoints.<peer>.lifecycle.<key>` with `shown` the value (a string, else compact JSON), as `server.<key>` entries are — so `(file, kind, name)` stays unique for every kind, `machine_diff`'s `~` pairing on that triple stays meaningful, the withheld line names each changed key once, and `_without_withheld` takes the peer from the name by stripping the fixed `extra_endpoints.` prefix and then `rsplit(".lifecycle.", 1)`: the key tail is a closed set that never contains `.lifecycle.`, so the last occurrence is unambiguous for any peer name, and `EndpointRef.name` is a bare `str` with no pattern (`qwen3.6` is a legal peer; a `split(".")` parse would yield `qwen3`, match no peer, and let a withheld lifecycle launch). The precedent is the `mcp_server` by-name removal (`loader.py:1588–1592`), not the dotted-`permission` rule, which is a dict path through `_put` and returns a list untouched. Existing installs adopt both new kinds once with no question. **The loader enforces withholding for all three kinds**, not just `launch` as today: a withheld `launch` or `launch_model` entry drops `server:` from both files for the run (attach-only); a withheld `peer_launch` entry removes that named peer's `lifecycle` from both files for the run, so `/model <peer>` can attach to it but never launch it — `_without_withheld` already removes list elements by `name` for `mcp_server`, and the per-peer rule mirrors it, removing only the named peer's `lifecycle` and leaving the peer attachable (`gpu: true` with `lifecycle=None` validates under `_lifecycle_requires_gpu` as an attach-only peer, tested). A later change to any key of any kind asks on a terminal or withholds as above. Secrets never enter the snapshot: `api_key` and `extra_headers` are siblings of `lifecycle` and are excluded by construction (a test asserts a peer carrying both contributes neither a name nor a `shown`). **`effort` is never a fingerprinted key**, and `/effort` writes only `server.effort` or `active_endpoint.effort`, so `machine_snapshot` is byte-identical before and after `/effort` on the primary and on a peer (tested), and `overrides.yaml` never gains an `api_key` from it (tested).
- **`/model` on vLLM, Ollama and LM Studio writes `server.model`, a `launch_model` key.** The origin signal is `ChannelAdapter.local_operator` — a class attribute that is true only on the terminal and the Zed/ACP channel, one channel per session; never `actor`, never message content (mobile queues text onto the same dispatcher). The REPL passes it as a new `persist_default_model(..., local_operator: bool = False)` argument from its channel. On `True` the one entry it changed is re-recorded in the same audited step through a new `trust.adopt_entries(global_dir, entries)`: the entry is **built from the value the REPL just wrote** — `{file: "overrides.yaml", kind: "launch_model", name: "server.model", shown: <model>}`, `machine_snapshot`'s own shape, `overrides.yaml` because that is where `persist_default_model` writes — never from a re-snapshot of the disk, which could carry an agent's write made in the meantime. It replaces the same-`(file, kind, name)` entry in `recorded_machine()["entries"]` **or adds it** — on the first terminal `/model` the record holds a `config.yaml` entry for `server.model` and none for `overrides.yaml`, which gains a `server:` block only now; a replace-only contract would merely ask once more at the next start, the safe side, but a needless question — keeps `kinds`, re-sorts with `machine_snapshot`'s key (`fingerprint` hashes list order; an unsorted record would make the next start re-record silently) and re-fingerprints — **never** `record_machine(dir, machine_snapshot(dir))`. Adoption covers one byte-identical entry: a value on disk that differs from the adopted one is still a diff and asks. The Zed/ACP channel adopts here although an ACP *start* cannot ask (asking is terminal-only, `start_cmd.py:691`); that asymmetry matches the gate's, which already trusts ACP as a local operator. `localharness model <name>` from the CLI passes nothing: the agent's own shell tool can run it, so "a CLI command" is no evidence of a person; it asks once at the next terminal start, as a change from a remote channel does. A hand edit of `config.yaml` asks as today.
- **Secrets.** The import path (§8) is the only new place a secret could enter config, and it routes keys to `SecretStr`; a process-named key **file** is opened only after a person confirmed its path and never under `--no-input`, so `init` cannot be made to read a file a listener points it at. `serve.log` keeps its promise because keys never reach `cmd`; the launch environment carries exactly one key variable, the record's, and no inherited `LLAMA_ARG_*` or key variable.
- **No code from files.** The GGUF reader parses bounded header fields and runs nothing; `nvidia-smi` runs through `which_outside_cwd` with list argv.
- **Relaunch is harness-owned only.** `free_accelerator` and `stop_server` act on the pidfile pid (now pid + start time), never on a foreign process.
- **`/effort` on Discord** persists through the audited overlay path with `actor="channel"` and the identity in `actor_detail`; it cannot relaunch anything, since no relaunch knob exists. (`/model` on Discord can relaunch; that is pre-existing and out of scope.)

## 12. Open questions

- Does the user's vLLM build expose a per-request reasoning budget (some reasoning parsers take a `thinking_budget`-style field)? Verified yes → it joins the capability table; no → vLLM runs on the client-side cut.
- Ollama's served window is VRAM-tiered and not settable per launch; the window line should say "Ollama decides" rather than a fit.
- Whether `init` should also write records for models Ollama/LM Studio already hold. Proposed: list them, do not duplicate them.

## 13. Out of scope

- Multi-GPU and tensor-parallel records.
- A preset marketplace or download-by-preset; `localharness model --download` stays as is.
- Per-turn effort (a `/effort` that lasts one message).
- Fingerprinting `extra_endpoints[*].lifecycle` was a pre-existing gap; it is closed here because the same code path is touched, not as a separate change.
