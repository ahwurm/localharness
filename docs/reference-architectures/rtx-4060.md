# Reference Architecture C — 8 GB consumer GPU

**Status: PROPOSED** (September 2026). Every number on this page was measured, but on a
**bandwidth-equivalent proxy** rather than on the target card — see
[How these numbers were measured](#how-these-numbers-were-measured). The
[practicality bar](README.md#practicality-bar) is met on the proxy; promotion to TESTED
requires the [validation checklist](#validation-checklist) on an actual 8 GB card.

This is the first architecture aimed at hardware the reader already owns rather than
hardware bought for the job: a desktop or laptop with a **discrete 8 GB GPU and 16 GB of
system RAM**.

## Summary

| | |
|---|---|
| Hardware | Discrete 8 GB GPU + 16 GB system RAM — reference part: **NVIDIA RTX 4060**, 8 GB GDDR6, 128-bit, **272 GB/s** |
| Model | [`empero-ai/Qwen3.8-9B-Distill`](https://huggingface.co/empero-ai/Qwen3.8-9B-Distill) — Qwen3.5-9B base, full fine-tune on ~70k Qwen3.8 2.4T-A95B teacher traces, Apache 2.0 |
| Quantization | GGUF `Q4_K_M` (5.38 GiB, [`empero-ai/Qwen3.8-9B-Distill-GGUF`](https://huggingface.co/empero-ai/Qwen3.8-9B-Distill-GGUF)) |
| Runtime | **llama.cpp** (`llama-server`), OpenAI API on `:8080` |
| Context served | **32k** at FP16 KV, or **64k** with `-ctk q8_0 -ctv q8_0` (both fit; see budget below) |
| Decode, single stream | **~39 tok/s measured** (shallow depth, both thinking modes) |
| Tool calling | **native**, via llama.cpp `--jinja` — the model's own Qwen3.5 template |

## Why this model — the bar math

The tier's constraint is the **8 GB of VRAM**, not the 16 GB of system RAM. A model that
fits VRAM entirely (`-ngl 99`, every layer offloaded) decodes at GPU bandwidth; a model
that spills even a few layers to the CPU decodes at system-RAM bandwidth, which is roughly
5× slower. So the question is only ever "what is the strongest model whose weights **plus**
KV cache **plus** the desktop's own VRAM use stay under 8 GB".

KV cost per token is set by the attention architecture. Qwen3.5-9B — and therefore this
distill, which is a full fine-tune of it and architecturally identical — uses a 3:1
linear:full hybrid, so only 8 of its 32 layers carry a KV cache.

| Candidate | Weights (Q4_K_M) | Fits 8 GB fully offloaded? |
|-----------|------------------|-----------------------------|
| Ministral-3-14B-Instruct-2512 | 7.67 GiB | ❌ weights alone exceed the usable card; partial offload only |
| GPT-OSS-20B | ~11 GiB | ❌ far past the card; heavy CPU spill |
| Gemma 4 12B QAT | ~7 GiB | ❌ no KV headroom left on an 8 GB card |
| **Qwen3.8-9B-Distill** | **5.38 GiB** | ✅ **~6.8 GiB total at 32k incl. buffers** |
| Gemma 4 E4B | ~3 GiB | ✅ fits easily — but a weaker general model (see below) |

**Measured KV cost: 33.0 KB/token at FP16.** This was measured, not derived — GPU memory
was sampled at three context sizes with everything else held constant:

| Context | KV type | GPU memory (measured) | Δ vs previous |
|---------|---------|------------------------|---------------|
| 8,192 | f16 | 5,408 MiB | — |
| 16,384 | f16 | 5,672 MiB | +264 MiB / +8,192 tok |
| 32,768 | f16 | 6,200 MiB | +528 MiB / +16,384 tok |
| 65,536 | **q8_0** | 6,520 MiB | — |

Both deltas give **exactly 0.0322 MiB/token = 33.0 KB/token**, and extrapolating to zero
context puts weights + compute buffers at **5,144 MiB**. The linearity is the useful part:
context cost on this tier is predictable to the megabyte.

### Memory budget (8 GB VRAM)

The proxy machine has unified memory, which can under-report weight residency versus a
discrete card. The honest projection for a **discrete** 8 GB card, where `-ngl 99` copies
the whole GGUF into VRAM, is therefore built from the file size plus the measured KV rate:

| Component | @ 32k, FP16 KV | @ 64k, q8_0 KV |
|-----------|----------------|-----------------|
| Weights (Q4_K_M, full offload) | 5.38 GiB | 5.38 GiB |
| KV cache (measured rate) | 1.03 GiB | 1.34 GiB |
| CUDA compute buffers | ~0.35 GiB | ~0.35 GiB |
| **Total resident** | **~6.8 GiB** | **~7.1 GiB** |
| Spare on an 8 GB card | ~1.2 GiB | ~0.9 GiB |

The spare column is what the desktop compositor and browser get to use. At 32k there is
room for an ordinary desktop; at 64k the machine wants to be headless or running a light
session. **64k at FP16 KV does not fit** (KV alone would be 2.06 GiB, pushing the total to
~7.8 GiB) — `q8_0` KV is what buys the 64k window, and it cost no measurable decode speed
(39.0 vs 39.4 tok/s) and no tool-calling accuracy in testing.

System RAM barely matters in this configuration: with every layer offloaded, the 16 GB
holds the OS and the harness's own Python process (a few hundred MB). Its role is to make
the *fallback* below viable, not the primary.

## Why this model — the tool-calling case

Criterion one for this project is not general capability, it is **tool-calling
reliability**, because a harness that cannot get a clean tool call cannot do anything at
all. Two properties decided it:

1. **Native tool calling in a template the harness already parses.** The distill inherits
   the Qwen3.5 chat template, which carries `tools` and emits `<tool_call>`. llama.cpp's
   `--jinja` path parses that into proper OpenAI `tool_calls` with no wrapper, no
   fine-tune, and no taught-XML fallback. It is the same family and the same call format
   as architecture A's 27B, so agent YAML and the harness's parser are unchanged.
2. **It is the strongest model in the tier that still fits fully offloaded.** The distill
   reports MMLU 0.546 → 0.751 over its Qwen3.5-9B base (GSM8K 0.885 → 0.870, a slight
   regression), which is a large general-capability gain bought without any change to the
   memory footprint.

**On the community ranking.** A September 2026 r/LocalLLM benchmark thread (u/37Scorpions,
RTX 4060 + 16 GB RAM) ranked eleven models on this exact hardware and put
**Ministral-3-14B Q4_K_M first**, with this distill second. That thread measured **general
capability with thinking disabled**, not tool calling, and this page deliberately reorders
its top two. The reason is the arithmetic above: Ministral-3-14B at Q4_K_M is **8.24 GB —
larger than the entire card** — so on 8 GB it can only run partially offloaded, at system-RAM
bandwidth for the spilled layers. It is the better model and the slower one here. Readers
with 12 GB or more should treat that ranking as the better guide; on 8 GB, the model that
fits wins.

*(The thread's permalink is not reproduced here: it could not be independently retrieved at
the time of writing, and this project does not print citations it has not verified.)*

## Serving

```bash
llama-server \
  --model Qwen3.8-9B-Q4_K_M.gguf \
  --alias qwen3.8-9b-distill \
  --host 127.0.0.1 --port 8080 \
  -c 32768 \
  -ngl 99 \
  --parallel 1 \
  --jinja \
  --threads 8
```

For the 64k window, add `-ctk q8_0 -ctv q8_0` and raise `-c 65536`.

- **`-ngl 99`** is the whole architecture. If `llama-server` reports fewer layers offloaded
  than the model has, the card is already occupied — close the browser or drop to 16k
  before accepting a partial offload.
- **`--parallel 1`** is load-bearing, exactly as on architecture B: recent `llama-server`
  builds default to several slots and silently divide `-c` among them, so a 32k launch
  becomes an 8k window per request. The harness is single-stream; one slot should own the
  whole window.
- **`--threads 8`** is a modest default for a 6–8 core consumer CPU. With full offload the
  CPU only handles sampling and the API, so this is not a throughput lever.
- Qwen-recommended sampling: `temperature 0.6, top_p 0.95, top_k 20`. The model card warns
  that **greedy decoding sends long generations into repetition loops** — do not set
  `temperature 0`.

## Performance

All figures single-stream at shallow prompt depth, `Q4_K_M`, full offload.

| Configuration | GPU memory | Decode | Tool calls |
|---------------|-----------|--------|------------|
| 32k, FP16 KV, thinking **on** | 6,200 MiB | **39.4 tok/s** | native ✓ |
| 32k, FP16 KV, thinking **off** | 6,200 MiB | **39.2 tok/s** | native ✓ |
| 64k, q8_0 KV, thinking on | 6,520 MiB | **39.0 tok/s** | native ✓ |
| 32k + `--spec-type ngram-cache` | 6,200 MiB | 38.4 tok/s | native ✓ |

Against the tier's speed target — 20 tok/s viable, 30 preferred — **this configuration
clears the preferred bar plainly, with no acceleration and no tricks.**

### Thinking on vs off

The distill is a reasoning model: its card states every answer opens with a `<think>` block
learned from the teacher traces, and documents no way to turn that off. **It can be turned
off anyway** — the inherited Qwen3.5 template honors the standard toggle:

```bash
--chat-template-kwargs '{"enable_thinking":false}'
```

Verified: with the flag, the `reasoning_content` field comes back empty and no `<think>`
span is emitted. What changes is **not the decode rate but the token count**:

| | Decode rate | Tokens to a finished answer | Tool calls |
|---|---|---|---|
| Thinking **on** | 39.4 tok/s | ≥800 (hit the test cap) | native, 3/3 harness rounds |
| Thinking **off** | 39.2 tok/s | 385–408 | native, 3/3 harness rounds |

Decode is bandwidth-bound and identical either way; thinking costs roughly **twice the
tokens, and therefore twice the wall-clock, per answer**. Tool-calling reliability was
unaffected in both modes.

**This page's recommendation assumes thinking ON**, matching how the harness is developed
and benchmarked elsewhere. Turn it off when latency matters more than reasoning depth — it
is a per-server flag, so it is a restart, not a per-request choice.

### Acceleration: what is and is not available here

- **n-gram speculative decode** (`--spec-type ngram-cache`) costs **zero extra VRAM** —
  measured at exactly the same 6,200 MiB — but produced **no gain** on generative output
  (38.4 vs 39.4 tok/s; drafts that miss cost a little). It only pays when output copies
  input verbatim. Not recommended on this tier.
- **MTP speculative decode** — an MTP draft head exists for this model
  ([`srmiles/Qwen3.8-9B-Distill-MTP-GGUF`](https://huggingface.co/srmiles/Qwen3.8-9B-Distill-MTP-GGUF),
  published at +30.5% decode and 81.4% draft acceptance) — but it needs **+3.85 GiB**, which
  does not fit alongside a 5.38 GiB model on an 8 GB card. This is a 12/16 GB-VRAM option,
  not an 8 GB one. It is listed here so readers stop looking for it.

Prefill/TTFT is **not** characterized on this page — see the measurement caveat below.

## How these numbers were measured

Measured on the maintainer's **DGX Spark (GB10, 273 GB/s)**, not on an RTX 4060, using the
real `llama-server` binary and the real harness. The transfer argument is narrow and
deliberate:

- **Decode transfers.** Single-stream decode of a fully-resident model is memory-bandwidth
  bound. The Spark's 273 GB/s and the RTX 4060's 272 GB/s are within 0.4% of each other, so
  the ~39 tok/s figure should hold on the target card to within a few percent. An RTX 4060
  **Laptop** is ~256 GB/s and should land proportionally lower (~37 tok/s).
- **Memory-footprint deltas transfer.** The 33.0 KB/token KV rate is an architectural
  property, not a hardware one.
- **Prefill/TTFT does not transfer, and is not reported.** It is compute-bound, and GB10
  Blackwell is far stronger than the 4060's AD107. Any TTFT number from this proxy would be
  optimistic and is therefore omitted rather than guessed.
- **Absolute weight residency is the soft spot.** The Spark's unified memory can
  under-report weight residency versus a discrete card, which is why the budget table above
  is built from the GGUF file size rather than from the proxy's own total.

This is why the page is PROPOSED, not TESTED.

## Harness configuration

`localharness init` detects this setup with no configuration. Against a live server it
reported, unedited:

```
✓ Runtime: llamacpp
✓ Tool calling: native
✓ Context budget: 32,768 tokens
```

A real session was then driven end to end against an isolated config directory — three
turns, three different tools, in both thinking modes:

| Turn | Tool | Result (thinking on) | Result (thinking off) |
|------|------|----------------------|------------------------|
| Read a file | `read` | ✓ exact contents returned | ✓ exact contents returned |
| Run a command | `bash_exec` | ✓ `uname -m` → `aarch64` | ✓ `uname -m` → `aarch64` |
| Write a durable fact | `remember` | ✓ fact stored | ✓ fact stored |

**6/6 tool rounds succeeded, native mode, no taught-XML fallback and no parse failures.**

To have the harness own the server's lifecycle, add a `server:` block so `localharness
start` relaunches it after a reboot:

```yaml
# <config_dir>/config.yaml
server:
  runtime: llamacpp
  binary: /path/to/llama.cpp/build/bin/llama-server
  model: /path/to/Qwen3.8-9B-Q4_K_M.gguf
  port: 8080
  extra_args: ["-c", "32768", "-ngl", "99", "--parallel", "1", "--jinja", "--threads", "8"]
```

No per-agent overrides are needed: the provider default `timeout_seconds` of 600.0 is
generous at ~39 tok/s, and the harness reads the served window from the runtime at startup.

## Fallbacks

| If | Use |
|----|-----|
| You have **12 GB+ VRAM** | [`Ministral-3-14B-Instruct-2512`](https://huggingface.co/unsloth/Ministral-3-14B-Instruct-2512-GGUF) Q4_K_M (8.24 GB) — native function calling, the stronger general model, and the community ranking's first place. Also the right pick if you accept partial offload on 8 GB and care more about answer quality than latency. |
| You want a **second vendor** at 8 GB | `Ministral-3-8B-Instruct-2512` Q4_K_M — same family's native function calling, comfortably resident, untested here. |
| **6 GB or less** | Gemma 4 E4B or a Qwen3.5-4B-class model (Q4_K_M ≈ 2.74 GB). Both have credible on-device tool calling; both are materially weaker general models. Untested here. |

## Validation checklist

Run on an actual 8 GB discrete card; promotion to TESTED requires the first three:

- [ ] **Decode ≥20 tok/s single-stream on the real card** (the tier bar; ≥30 preferred)
- [ ] **Full offload confirmed** — `llama-server` reports all layers on GPU, with a desktop session running
- [ ] **Tool-call success through a real harness session**, native mode, no taught-XML fallback
- [ ] Decode at 16–32k prompt depth, not just shallow (this page's figures are shallow-depth)
- [ ] TTFT cold vs prefix-cached at 8k/32k — the number this proxy could not produce
- [ ] 64k `q8_0` KV run: quality delta vs the FP16 32k window on `bench/` scenarios
- [ ] Behaviour when the card is contended (browser open, compositor active) — where partial offload starts
- [ ] Thinking-mode token accounting against `max_tokens` (gaps §6)

**If decode misses 20 tok/s on the real card:** check the offload count first — a silent
partial offload is by far the most likely cause, and it is what the `--parallel 1` and
`-ngl 99` notes above exist to prevent.
